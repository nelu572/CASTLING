# 레벨 디자인 절차

레퍼런스 분석, 레벨 기획·공간 설계, 승인안의 Unity 적용, 레벨 검증·개선 요청에 사용한다. 목표 경험에 맞춰 설계 방식과 평가 기준을 선택한다. 에셋 편집만 필요한 작업은 기존 룸·타일 안내를 사용한다. 이 파일은 프로젝트의 기존 파일형 절차이며 전역 설치 스킬·자동 생성기가 아니다.

## 정보의 분리

| 정보 | 관리 위치·읽는 시점 |
| --- | --- |
| 범용 판단·워크플로 | 이 절차. 레벨 작업 진입 시 읽는다. |
| 현재 프로젝트의 기획·능력·기믹·좌표계·도구 | [프로젝트 근거](../../.reference/guides/LEVEL_DESIGN_CONTEXT.md). 필요한 실제 코드·Editor로 확인한다. |
| 작품별 관찰과 적용 범위 | [레퍼런스 분석 자료](../../.reference/guides/LEVEL_DESIGN_REFERENCES.md). 이번 요청에 선택한 자료만 읽는다. |
| 개별 레벨의 설계·측정·플레이 기록 | [설계 양식](../../.templates/LEVEL_DESIGN_TEMPLATE/template.md)을 사용해 [.work](../../.work/README.md)에 둔다. 승인된 장기 결정은 [자료 추가 기준](../harness/TEMPLATES.md)을 따른다. |
| 보존할 독립 레벨의 목록·핵심 해법·재사용 안내 | [레벨 보관소](../../.reference/levels/README.md)와 레벨 카드. [카드 양식](../../.templates/LEVEL_LIBRARY_TEMPLATE/template.md)으로 추가하고 확인 범위·승인 근거를 연결한다. |

개별 테스트는 하네스를 평가하는 사례다. 특정 스테이지나 기믹을 이후 작업의 상시 목표로 삼지 않는다. 다른 프로젝트의 문서·설정을 가져오지 않고 현재 프로젝트의 사실을 위 구조에 연결한다.

## 작업 범위와 진입

1. `AGENTS.md`와 [Notion 안내](../../.reference/notion/NOTION_GUIDE.md)에서 관련 원문을 읽는다. Chapter_01이면 [제작 결정](../../.reference/records/CHAPTER_01.md), 독립 레벨이면 [레벨 보관소](../../.reference/levels/README.md)의 해당 카드와 [독립 레벨 결정](../../.reference/records/LEVEL_COLLECTION.md)을 읽고 날짜가 뒤인 변경 결정을 확인한다.
2. [프로젝트 근거 안내](../../.reference/guides/LEVEL_DESIGN_CONTEXT.md)에서 이번 단계에 필요한 코드·에셋 안내를 찾는다. 현재 능력·수치는 실제 코드와 Editor에서 다시 확인한다.
3. 현재 장르·플레이 방식, 대상·요청 단계, 목표 경험·난이도, 레퍼런스, 기술 제약과 변경 허용 범위를 짧게 정리한다. 사용자가 적지 않은 조건은 기획·구현에서 파악하고 가정을 표시한다. 중요한 미확정 규칙·목표 충돌만 질문하며, 영향 없는 분석·조건부 설계는 이어간다. 분석·설계 요청이면 해당 산출물까지 완료하고 씬은 수정하지 않는다.
4. 신규 설계 / 기존 레벨 수정 / 핵심 경험을 유지한 공간 재설계 / 평가 중 이번 범위를 정한다. 기존 수정은 보존할 동선·상태를, 재설계는 보존할 경험·기믹과 바꿀 연결 구조·시작/목표·배치·카메라를 적는다. 좌표 보존을 재설계의 기본 제약으로 만들지 않는다.
5. 양식은 요청 단계에 필요한 항목만 채운다. 선택한 설계 전략·우선 평가 기준·완료 조건을 구현 전에 기록하고, 검증 결과에 맞추려고 목표를 사후 변경하지 않는다. 목표를 바꾸면 이유와 승인 범위를 남긴다.

| 단계 | 완료 산출물 | 다음 단계 조건 |
| --- | --- | --- |
| 분석 | 출처가 있는 레퍼런스 관찰·현재 제약·미확인 목록 | 설계에 영향을 주는 미확정 규칙을 식별 |
| 기획 | 핵심 경험·목표·사용 기믹·난이도 가설 | 요청·기획과 맞는 방향 |
| 설계 | 선택한 전략에 맞는 공간도·행동/경로·실수/복구·배치·평가 계획 | 구체 설계안에 대한 사용자 승인 |
| 구현 | 승인 범위의 Tilemap·기존 오브젝트 적용 | 실제 저장 상태와 참조 확인 |
| 검증 | 기술·게임플레이·공간 평가와 각 증거 수준을 구분한 보고 | 필수 미실행·실패 항목 공개 |
| 개선 | 의도와 관찰의 차이·개선 가설·변경·관련 재평가 | 기존 승인 범위 또는 변경안 승인 |

## 1. 분석

### 프로젝트 제약

[Unity 하네스](../harness/UNITY.md)에 따라 기존 stdio MCP의 `mcpforunity://instances`를 읽고 프로젝트 경로·이름을 대조한다. 복수 연결이면 일치하는 인스턴스를 고정한다. 현재 활성 씬·로드된 씬·Edit/Play Mode와 사용자 변경을 확인한다. 이름만 같은 다른 프로젝트에서 작업하지 않는다.

MCP 연결이 없으면 Editor 분석·구현·플레이 검증은 실행할 수 없다고 알린다. 파일 기반 코드 분석과 조건부 설계는 계속할 수 있지만, 씬 YAML·외부 CLI·별도 HTTP 서버로 Editor 확인을 우회하지 않는다. 패키지 설치는 이 절차가 허가하지 않으며 해당 요청과 프로젝트 공통 지침을 따른다.

설계 전 다음을 근거표에 기록한다. 각 항목을 **현재 Editor 확인 / 코드 확인 / 추정 / 미확인**으로 구분하고 단위·시점·대상을 쓴다.

| 대상 | 필요한 확인 |
| --- | --- |
| 플레이어 몸체 | 조작 대상별 Collider 종류·형상·offset·월드 크기·Transform Scale, 실제 충돌 경계 |
| 이동 | 연결된 Settings, 가감속·최대 속도·중력·하강 배율·점프·코요테/버퍼, Rigidbody2D·충돌 재질·고정 시간 간격·레이어 충돌 |
| 특수 능력·상호작용 | 실제 입력·발동/종료 조건, 위치/속도/상태 처리, 지형·다른 대상과의 상호작용 |
| 타일 좌표계 | 대상 Grid/Tilemap의 셀 크기·간격·layout/swizzle·원점·부모 변환·tileAnchor·셀 변환, 셀↔월드 대응 |
| 에셋·기믹 | 현재 Tile/Prefab 경로와 하위 에셋 식별, 배치·활성화·참조 상태, 시각과 충돌 형상의 차이 |
| 화면 | 활성 카메라·화면비·viewport·추적·줌·경계, 주요 활동 순간의 플레이어와 장치·지형의 가시 영역 |
| 진행 | 실제 Entry·시작점, 목표/Exit의 존재·활성 조건, 실패·복귀·재시작 경로 |

코드의 기본값이나 이상적인 포물선만으로 실제 점프 높이·거리·통과 폭을 확정하지 않는다. Collider·설정 에셋·실제 물리와 입력을 포함한 Play Mode 측정이 필요하다. 정지/달리기 점프·특수 이동·협동 동작 등 필요한 조건을 나눠 출발 속도·착지 높이·천장/벽·입력·재현 여유를 기록한다. 최고 기록을 초보자 통과 기준으로 쓰지 않는다. 측정 전 설계는 가설로 표시하고 그 수치가 필요한 구현을 보류한다.

### 레퍼런스

- 게임 이름과 작품/버전, 관찰할 스테이지·영상 시간대, 참고할 요소를 정한다. 여러 게임이면 같은 항목으로 비교하고 어떤 요소를 어느 작품에서 취할지 쓴다.
- 실제 확인한 설명·이미지·플레이 영상은 URL/제공 파일·시점·장면/타임코드를 남긴다. **확인한 사실 / 관찰의 해석 / 현재 프로젝트 적용 가설 / 자료 부족**을 분리한다. 이름만으로 플레이 장면이나 난이도 곡선을 봤다고 쓰지 않는다.
- 공간·지형, 요구 행동과 판단/발견, 기믹/장애물, 난이도/학습, 동선/리듬, 실루엣/비율/개방과 폐쇄, 화면 가독성 중 요청에 필요한 축을 선택한다. 정지 화면만으로 충돌·시간 조건·풀이·기믹 작동을 확정하지 않는다.
- 자료가 부족해 설계 판단이 달라질 때 사용자에게 스크린샷·영상·관심 구간을 요청한다. 제공 전에도 확인된 근거로 분석을 마치고 나머지를 조건부로 남길 수 있다.
- 맵 윤곽·배치·풀이 순서를 복제하지 않는다. 관찰한 원칙을 현재 프로젝트의 능력과 목표에 맞게 변환하고 달라지는 이유를 쓴다. 레퍼런스의 멀티플레이 인원·열쇠·장치·물리를 현재 기능으로 가정하지 않는다.

현재 요청의 레퍼런스와 채택/제외할 원칙을 기록한다. 작품·목표가 바뀌면 이전 프로필의 적용 여부를 다시 판단하며, 이전 게임의 평지·정밀도·인원수·공간 구성을 자동으로 이어받지 않는다. 같은 요청의 유효한 선택은 유지한다. 미지정이면 현재 기획과 요청에서 방향을 추론해 밝히며 특정 게임을 강제 기본값으로 삼지 않는다. 필요한 작품의 확인된 분석이 없으면 자료를 조사하거나 미확인으로 남기고 조건부 설계를 진행한다.

## 2. 기획

- 핵심 경험을 한 문장으로 정하고 목표 행동과 완료를 관찰할 기준을 함께 쓴다.
- 현재 사용 가능한 능력·기믹에서 이번 경험에 필요한 것을 선택한다. 매 레벨에 모든 능력이나 같은 장치를 사용할 필요는 없다. 코드 존재와 대상 씬에서 작동함을 구분한다. 플레이어별 기여와 제한은 현재 프로젝트 기획·구현을 따른다.
- 기존 기능만으로 목표를 달성하기 어렵다면 목표/공간의 조정과 새 기믹·상호작용 제안을 비교한다. 제안의 기대 효과·필요 변경·기존 동작에 미칠 영향·검증 방법을 적고 구현과 분리한다. 사용자가 기존 기능만 허용하면 그 범위를 지키며, 승인 없이 공용 시스템을 변경하지 않는다.
- 난이도는 필요한 축으로 설명한다. 예: 조작 정밀도·반응/연속 수행, 규칙 이해·선택/조율, 방향 판단·정보 탐색, 실패 후 손실. 미확정 물리·능력 제한·퍼즐 규칙을 새 사실로 정하지 않는다.

### 설계 방식과 평가 기준 선택

목표 경험과 핵심 상호작용을 먼저 정하고 적합한 공간을 고른다. 이동 지형 자체가 핵심이면 움직임과 형태를 함께 시험하며 발전시킨다. 아래는 선택 예시이며 고정 분류·필수 구성이나 특정 게임의 사실이 아니다. 조합하거나 새 방식을 정의할 수 있다.

| 중심 경험 | 설계에서 먼저 볼 것 | 우선 평가할 것 |
| --- | --- | --- |
| 이동·점프 숙련 | 실측 동작 범위, 접근/도약/착지, 도전과 회복의 리듬 | 요구 정밀도·난이도 상승·재시도 비용·다른 능력 경로 |
| 협동·상호작용 | 역할·의존 관계·서로 준비하는 상태 | 각자의 기여·조율·대기·대안의 협동 보존 |
| 논리 퍼즐 | 관찰 정보·상태 전이·선택과 반례 | 추론의 성립·피드백·해법의 범위·복구 |
| 탐험·공간 발견 | 경로 연결·시야/정보·분기/귀환의 의미 | 선택의 차이·방향 파악·발견·되돌아감의 가치 |
| 학습·기믹 응용 | 소개할 규칙과 이미 배운 행동의 조합 | 이해·새 맥락으로의 전이·과부하·반복의 효용 |

이번 전략의 선택 이유와 평가의 우선순위를 기록한다. 평지·열린 공간·짧은 동선·얇은 지형·단일 정답을 공통 성공 조건으로 삼지 않는다. 필수 기준과 탐색할 가설을 구분하고, 불필요한 항목은 이유와 함께 제외한다.

## 3. 설계와 승인

1. 선택한 경험에 맞춰 공간의 연결·제한·활동면을 설계한다. 특정 윤곽이나 발판 반복을 표준 형태로 삼지 않는다.
2. 시작부터 목표까지의 행동·판단·정보와 플레이어별 동선을 연결한다. 이동이면 동작과 리듬, 퍼즐이면 상태 전이, 탐험이면 분기·발견·귀환 등 목적에 맞는 표현을 고른다. 전체 구조와 구현용 좌표는 분리할 수 있다.
3. 구간의 이동·대기·반복·빈 공간이 경험에 기여하는지 평가한다. 연습·긴장·휴식·관찰·방향 학습·귀환의 의미가 있으면 유지하고, 목표를 돕지 않는 비용을 줄인다. 짧아지거나 복잡해진 사실만으로 개선으로 판단하지 않는다.
4. 선택한 능력·기믹의 상태, 의도한 행동, 중단·역순·오용·추락·실패 뒤의 복구를 기록한다. 현재 프로젝트에서 필요한 충돌·속도 유지·교환 등 조합 조건은 근거 안내로 확인한다. 대안 경로는 재현 조건과 함께 목표 경험·학습·역할/난이도·기술 안전에 미치는 영향을 평가해 허용 / 조정 제안 / 차단 제안과 이유를 남긴다. 의도한 순서와 다르다는 이유만으로 제거하거나, 협동이 남는다는 이유만으로 자동 수용하지 않는다.
5. 공간도에 셀/월드 좌표의 기준·단위·방향·범례를 붙인다. 지형 구간, 장치, 시작/목표, 복구 지점, 카메라 경계를 식별자로 연결한다. 좌표 미측정이면 개념도라고 쓰고 승인된 정확한 배치로 취급하지 않는다.
6. 목표 경험에 필요한 단서·상태 피드백·가독성과 도전/휴식의 리듬을 정한다. 학습 레벨이면 소개와 응용의 차이를, 탐험이면 발견 전후 정보의 차이를 다룬다. 화면과 시야 제한은 현재 플레이 방식에 맞춰 확인한다.
7. 변경할 Tilemap·셀 범위·기존 오브젝트·참조·카메라를 명시하고 검증 기준과 미확정 사항을 붙여 설계안을 제시한다. 사용자에게 승인받을 구체 버전을 남긴다.

### 지형의 목적과 실루엣

- 지형은 구간이나 같은 역할의 묶음별로 경험에 대한 기여를 설명한다. 직접적인 이동·퍼즐 기능 외에 시선 유도·방향 단서·스케일감·분위기·리듬·안전한 관찰도 역할이다. 타일마다 개별 기능을 의무화하지 않는다.
- 세부 배치 전에 활동면·연결·실루엣을 경험과 함께 검토한다. 길이·높이·두께·질량·빈 공간은 몸체와 실제 이동 범위, 표현할 경험에 맞춰 결정한다. 크고 두꺼운 덩어리나 단차·장애물도 그 기여를 비교하며, 최소/최대 타일 수나 일률적인 얇음을 품질 기준으로 삼지 않는다.
- 열린 방향과 닫힌 방향을 비교해 각각의 이동·시야·긴장·안전·공간 분리 효과를 선택한다. 개방이나 폐쇄를 먼저 정답으로 두지 않는다. 경계가 바뀌면 이탈·대안 경로·복구와 새 착지면도 함께 검토한다.
- 실제 이동 영역, 충돌 형상과 외형, 충돌 없는 배경, 카메라 프레이밍을 구분한다. 어두운 영역을 곧바로 충돌로 보거나 화면 경계가 이동을 막는다고 가정하지 않는다. 상태에 따라 변하는 구조는 각 상태의 충돌·외형·가시성을 따로 확인한다.

**기본 중단점은 설계안 제시 후 승인 대기다.** “레벨을 만들어 달라”는 요청만으로 새 설계안을 자동 승인하지 않는다. 이전에 구체 설계와 적용 범위가 승인됐고 그 적용을 요청받았다면 반복 승인 없이 구현한다. 변경 시점에 실제 상태가 설계의 전제와 달라졌으면 사용자 튜닝을 덮어쓰지 말고 차이와 영향을 제시한다. 새 기믹·조작/물리·목표/풀이 구조의 중요한 변경은 승인 범위를 다시 확인한다. 승인 범위 안의 통상적인 배치 조정·수정·검증마다 재승인을 요구하지 않는다.

## 4. 구현

구현을 요청받고 해당 설계가 승인된 경우에만 진행한다. [Unity 하네스](../harness/UNITY.md), [룸 만들기](../../.reference/guides/ROOM_AUTHORING.md), [플랫폼 타일](../../.reference/guides/PLATFORM_SHEETS.md), 필요 시 [배경 조립](../../.reference/guides/BG_STRUCTURE_MODULAR.md)을 따른다.

- 현재 씬의 `RoomTransitionController` 참조로 작업 Grid·RoomArea·Entry를 확인하고 비활성 보관용 초안과 다른 씬은 제외한다. 룸 분할은 기존 룸 안내에 따라 카메라·진행 단위로 결정하며 기믹마다 기계적으로 나누지 않는다.
- 씬·타일·컴포넌트·프리팹은 Unity MCP로 적용한다. 범용 `execute_code`가 보인다는 이유만으로 검증된 Tilemap 배치 도구가 있다고 보고하지 않는다. 사용 중인 도구의 지원 범위와 Undo·저장·충돌 갱신을 확인한다.
- 기존 Tile 하위 에셋·셀 변환·색·Physics Shape·참조를 보존한다. 팔레트 프리팹을 플레이 지형으로 배치하지 않는다. 타일/외곽선 갱신은 기존 안내를 사용한다.
- 요청에 없는 기능·생성기·패키지는 추가하지 않는다. 구현한 상태와 설계의 차이를 남기고 저장 후 참조와 실제 충돌을 검증한다.

## 5. 검증

[Unity 변경 검증](UNITY_VERIFY.md)과 [재사용 검사](../../.reference/guides/VERIFICATION_CHECKS.md)를 실행 범위에 맞게 사용한다. 아래는 판정 기준이며 자동 실행 도구의 목록이 아니다. 시작/목표가 없는 테스트 구간은 승인된 종료 지점으로 범위를 명시하고 챕터 완주라고 쓰지 않는다.

| 평가 축 | 확인할 결과 | 증거와 한계 |
| --- | --- | --- |
| 기술 | 실제 입력으로 출발→목표, 이동·충돌·기믹 반응, 진행 불가·복구·참조 | 코드/Editor 검사와 실측·연속 입력·실패 사례. 실행한 조건·경로만 확인한 것으로 보고한다. |
| 게임플레이 | 목표 경험·기믹의 의미·판단/선택·의도/대안 경로·난이도/학습·리듬 | 행동/상태/시간 기록을 의도와 대조하고 사람이 이해·조율·체감하는지 확인한다. 사용 횟수나 통과만으로 기여·재미를 확정하지 않는다. |
| 공간 디자인 | 실루엣·배치/비율·연결 구조·개방/폐쇄의 적절성·가독성·카메라 | 실제 Game View와 필요 시 공간도를 함께 읽는다. 화면 포함 여부가 좋은 구도를, 충돌면의 기능 존재가 크기·형태의 적절성을 보장하지 않는다. |

선택한 설계 전략의 기준으로 세 축을 각각 판정한다. 방법/증거 수준은 별도 표기한다: 코드·정량 검사 / 실제 입력 경로 / 스크린샷·AI 비평 / 사람 플레이. 자동화할 수 있어도 실행 도구나 결과가 없으면 미실행이다. 관찰 가능한 구조·행동의 문제는 사람 플레이 전에도 평가하되, 재미·체감 난이도의 검증과 구분한다.

자동 입력은 실행한 입력 경로의 증거다. 위치·속도를 직접 쓴 구도/사례 검사는 연속 완주와 구분한다. 유한한 사례로 모든 막힘·우회가 없음을 증명하지 않는다. 사람 플레이가 필요한 발견성·체감 난이도·재미는 자동 입력으로 통과 처리하지 않는다.

각 기준에 **통과 / 실패 / 미실행 / 해당 없음(이유)**, 실행 조건과 관찰 결과를 남긴다. 설계·구현·입력 경로·세 평가 축·사람 플레이의 확인 상태를 각각 보고한다. 필수 검사가 미실행·실패이면 **검증 미완료**다. 기술 통과나 설계·참조·스크린샷만으로 좋은 레벨 또는 재미가 검증됐다고 보고하지 않는다.

## 6. 개선

기술 검사를 통과한 뒤에도 목표에 비추어 게임플레이와 공간을 스스로 비평한다.

1. 주요 진행/실패/회복·선택 순간의 실제 Game View와 입력 결과를 확보하고 직접 읽는다. 캡처의 위치·해상도·카메라·장치 상태를 남긴다. 배치한 구도는 실제 플레이와 구분한다.
2. 의도한 행동·판단·리듬과 관찰 결과의 차이를 구간/경로에 연결한다. 지형·정보·기믹·이동·카메라 중 원인과 가설을 구분하고, 가장 중요한 문제의 영향과 개선안을 정한다. 기술 실패뿐 아니라 목표와 맞지 않는 단조로움·과부하·과한 제한·발견성도 대상이다.
3. 허용된 수정 범위에서 바꾸고 관련 경로·실패/복구·화면을 다시 확인한다. 연결 구조를 바꿔야 하면 공간 재설계로 다룬다. 중요한 설계/공용 규칙 변경은 승인용 제안까지 구체화한 뒤 승인받는다. 능력·물리를 바꿔 문제를 숨기지 않는다.
4. 같은 조건의 전후 증거로 가설을 평가한다. 구도 등 조건을 바꾸면 차이를 명시한다. 새 문제가 생겼거나 필수 기준이 남으면 반복하고, 요청한 완료 조건이 충족되면 멈춘다. 사람 플레이·자료·승인이 남으면 그 상태와 다음 확인을 보고하며 무한한 임의 개선을 계속하지 않는다.

발견을 **레벨 한정 / 기믹·프로젝트 한정 / 범용 후보**로 구분한다. 범용 후보는 다른 목표·구조에도 같은 원인이 적용되는지와 반례·부작용을 검토한 뒤 기존 절차에 최소 반영한다. 단일 사례의 타일 두께·카메라 값·정답 순서를 공통 규칙으로 올리지 않는다. 일회성 설계·측정·플레이 원자료는 작업 폴더에, 보존할 독립 레벨의 핵심 해법·평가·확인 범위는 보관 카드에, 승인 결정은 제작 기록에 둔다. 프로젝트 기능 사실은 근거 안내에, 작품 관찰은 레퍼런스 자료에 둔다. 새로 재현한 버그의 이슈 처리는 `AGENTS.md`를 따른다.

## 요청 예시

- `현재 기능으로 평지형 협동 레벨을 설계해 줘. 기여와 인계를 우선하고 대안 풀이의 영향을 평가해 줘. 설계까지만 해 줘.`
- `Celeste를 참고하되 실제 확인 자료를 구분하고, 현재 이동 능력으로 중급 점프 숙련 구간을 설계해 줘. 원작 능력을 추가한 것으로 가정하지 마.`
- `탐험과 경로 선택 중심 구간을 설계해 줘. 분기의 차이와 발견·귀환의 가치를 평가하고 현재 프로젝트의 공유 카메라 제약을 확인해 줘.`
- `앞서 승인한 설계안 v2의 Room_01 지정 범위만 적용하고 이동 물리는 유지해 줘. 기존 Unity 검증과 실제 입력 경로를 확인해 줘.`
- `현재 레벨을 수정하지 말고 도달성·퍼즐·막힘·카메라를 검증해 줘. 자동 입력 결과와 사람 플레이 대기 항목을 나눠 보고해 줘.`
