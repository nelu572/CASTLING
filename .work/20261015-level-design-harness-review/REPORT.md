기존 문서에도 일률적 얇음과 대안 제거를 경계하는 문구는 있었다. 모든 항목이 명시적인 절대 규칙이었다고 주장하지 않는다. 보완의 목적은 실제 작업에서 특정 사례의 취향과 수치를 공통 합격 기준으로 사용하지 않도록 하는 것이다.

## 전체 작업 흐름

1. 현재 게임·기획·요청 단계·목표 경험·난이도·허용 범위를 이해한다. 부족한 조건은 프로젝트에서 조사하고 중요한 불확실성만 질문한다.
2. 실제 능력·상호작용·기믹·충돌·좌표·화면·완료/복구 조건의 근거를 확인한다. 코드 존재와 대상 씬의 작동을 구분한다.
3. 레퍼런스의 확인 사실·해석·적용 가설·자료 부족을 나누고 필요한 원칙만 추출한다. 다른 작품으로 바뀌면 이전 기준의 적용을 재검토한다.
4. 이동 숙련·협동·논리·탐험·학습 등의 전략을 선택/조합하고 이번 레벨의 우선 평가 기준을 정한다. 이 목록은 고정 분류가 아니다.
5. 목표 행동·판단·정보·상호작용에 적합한 공간을 설계한다. 신규, 기존 수정, 핵심 경험 유지 재설계의 보존 범위를 구분한다.
6. 의도/대안 경로·실패/복구를 검토한다. 기존 재료로 부족하면 새 기믹의 효과·영향·검증을 제안하되 승인 없이 공용 시스템을 변경하지 않는다.
7. 설계 승인 후 요청 범위를 구현하고 실제 입력과 Game View를 확인한다. 설계만 요청되면 해당 단계까지만 수행한다.
8. 기술·게임플레이·공간을 각각 평가한다. 코드/정량, 실제 입력, 화면·AI 비평, 사람 플레이는 별도의 증거 방법이다.
9. 관찰과 의도의 차이 → 원인/개선 가설 → 허용 범위의 변경 → 전후 비교·관련 재검증을 반복한다. 완료 조건과 사람 플레이·자료·승인 대기를 명시한다.

개별 발견은 레벨 한정 / 기믹·프로젝트 한정 / 범용 후보로 구분한다. 다른 목표·구조에서의 원인과 반례를 검토한 뒤에만 공통 절차에 최소 반영한다.

## 세 가상 요청의 모의 점검

하네스 수정 뒤, 이전 감사 결론과 의도한 답을 주지 않은 별도 컨텍스트의 보조 에이전트가 수정 문서를 읽고 아래 요청을 A→B→C 순서로 처리할 계획을 작성했다. 파일/Unity/외부 서비스 변경과 실제 레벨·좌표 제작을 금지한 문서 기반 점검이었다.

| 요청 | 관찰한 전략·예상 산출물 | 우선 평가 기준 | 확인 범위와 미확인 |
| --- | --- | --- | --- |
| A. PICO PARK 참고, 평지형 협동 상호작용 | 역할·상태 의존·실패/복구·대안 분석 계획 | 양쪽 기여·조율·대기 의미, 기술 작동/막힘, 두 몸체·장치의 읽힘 | 평지를 이번 요청의 제약으로만 사용. 기록된 소개·이미지 범위를 넘어 실제 정답·난이도 곡선을 확인했다고 하지 않음 |
| B. Celeste 참고, 중급 이동·점프 숙련 | 실측 조건, 접근/도약/착지, 도전/회복 리듬 계획 | 정밀도·연속 수행·난이도 상승·재시도 비용, 실제 능력 조합·착지·공유 화면 | A의 평지·필수 장치를 승계하지 않음. Celeste 분석 자료 없음, 대시/벽타기 미확인, 도달 수치 미측정을 명시 |
| C. 레퍼런스 미지정, 탐험·경로 선택 | 연결/정보, 선택 차이, 발견/귀환과 분리/재합류 계획 | 선택의 의미·방향 파악·귀환 가치, 경로별 도달/역행/복구, 분기·재연결의 읽힘 | 특정 작품을 기본값으로 선택하지 않음. 지도·수집·저장 기능을 가정하지 않고 왕복의 가치를 평가 |

세 요청 모두 절차 계획은 질문 없이 조건부로 완료할 수 있다고 판단했다. 원작 장면 채택, 구체 난이도와 대상 플레이어의 확정, 새 시스템·목표 규칙이 필요해질 때만 중요한 질문을 남겼다. 현재 프로젝트의 2인 기여와 공유 화면 제약은 유지했다.

**결과:** 서로 다른 전략·산출물·평가 기준의 선택, 이전 기준의 자동 상속 방지, 미구현 능력의 가정 방지를 관찰했다. 진행을 막는 문서 간 충돌은 보고되지 않았다. 이는 가상 레벨의 구현·기믹·도달·재미 검증 또는 모든 향후 요청의 성공을 입증하지 않는다. 가상 레벨의 Unity 플레이와 사람 플레이는 미실행이다.

## 이전 레벨 테스트가 제공한 근거

다음은 로컬 작업 기록의 요약이다. 해당 원본 보고서·스크린샷·개발 씬은 이번 문서 전용 커밋에 포함하지 않는다. 누락된 로컬 자료로 연결되는 링크도 두지 않는다.

- 초기 Dev_PressureRelay: 실제 입력·문/스위치 기능이 작동해도 지형 만족도가 낮을 수 있었다.
- O1: 경계를 제거하는 단순화가 핵심 경험에서 공간을 다시 설계한 결과와 같지 않았다. 제안 단계였고 새 구조 플레이 검증은 아니었다.
- D1·D2·D3 비교: 서로 다른 연결 구조를 제안했으나 세 안을 모두 실제 플레이한 것은 아니었다.
- D3 구현: 정상 인계·하강과 실패/복귀를 실제 입력으로 확인했다는 기록이 있다. 공중 문 점유로 B를 생략하는 협동 대안도 확인됐으며, 기능 작동·가시성 통과가 U자 비율·판단의 깊이·완료 가독성을 입증하지 못했다.
- 후속 지형 비평: ‘최소 지형’이라는 과한 판단을 철회하고 형태 정돈과 공간 재설계를 구분했다. 후속안은 구현·플레이 검증 전이었다.

이 사례들은 공통 평가와 정보 분리를 개선할 근거다. 특정 타일 두께·좌표·카메라 값·필수 풀이를 공통 규칙으로 승격하지 않았다. 위 Unity 결과는 과거 기록의 요약이며 이 브랜치에서 재현한 결과가 아니다.

## 현재 한계와 다음 검증

기존 MCP는 조사·편집·캡처 수단이고 프로젝트에는 룸·타일·외곽선 도구가 있다. 그러나 조건별 이동 실측, PlayerInput 재현과 상태 복원, 진행별 입력/기믹/화면의 연결, 능력 조합을 반영한 도달·퍼즐 반례 탐색을 묶은 전용 러너는 아직 없다. 일반 C# 실행 기능이 이런 도구의 구현·검증을 뜻하지 않는다.

다음 우선순위는 다른 유형의 요청을 실제 설계→승인된 소규모 구현→세 축 평가·사람 플레이까지 적용하는 교차 검증이다. 이후 반복되는 병목만 자동화한다. 자동 입력·수치·스크린샷 비평으로 재미·체감 난이도·발견성이 검증됐다고 주장하지 않는다.

## 외부 검토 패키지 검증

기존 개선 작업에서는 AGENTS→절차→프로젝트/작품/양식과 Unity 검증 역참조를 포함한8개 문서의 로컬 링크/앵커108개를 확인해 문제0이었다. 이는 당시 로컬 작업 트리의 결과다. 외부 검토 패키지는 스테이징 후 실제 Git 인덱스의 파일만 사용해 별도 검증했다. 문서10개와 로컬 링크118개(앵커1개 포함)의 누락은0이며, `git diff --cached --check`를 통과했다. 변경 파일은 모두 작은 Markdown이고 총량은 약76KiB다. 토큰·개인키·개인 경로·이메일·인증값 패턴 검사와 변경 범위 검토에서 문제를 발견하지 못했다.

검토 범위는 문서10개(하네스8개와 이 폴더의 README/REPORT)이며, 다른 `.work` 자료·인증 설정·로그·바이너리·Unity 변경은 제외한다. 저장소의 기존 무시 규칙은 변경하지 않는다.
